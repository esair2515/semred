Redaction lifecycle

A staged, inspectable redaction lifecycle.

Semred separates deterministic coverage from contextual review. Each applied change is inspectable, and the run records which stages actually completed.

Press Play to see the other four stages · 7s

Detect

Deterministic rules run first. When enabled, an LLM reviews the partially redacted text for contextual or indirect identifiers, and every proposed action is validated before application.

Canonicalize

Overlapping and duplicate spans are normalized within each stage, with stable labels and conservative conflict handling before that stage rewrites text.

Rewrite

Accepted spans are replaced locally with stable placeholders. Unchanged source text is preserved rather than silently regenerated.

Score

A similarity score compares the source and result. Embeddings are used when enabled and available; otherwise a deterministic lexical fallback is used. It is not a safety or coverage score.

Audit

Every applied replacement records its type, source value, replacement, stage, and review metadata. Audit trails can be exported as JSON or CSV.

Stated plainly

What Semred does not claim.

Redaction tools that promise completeness are the ones that get people hurt. Here is where our guarantees stop.

A high score is not safety

Semantic similarity describes how much meaning survived. It says nothing about whether every sensitive span was found.

Zero records is not a clean document

An empty replacement list means nothing matched — not that there was nothing to match. Review still applies.

Review stays in the loop

Semred is built to make human review fast and evidence‑backed, not to remove it. Spans the model alone proposed are flagged as such.
